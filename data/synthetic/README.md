# Synthetic data (augmentation only — never a training/test ground truth)

## `chf_synthetic_gp_augmented.csv`

7,114 synthetic (P, G, X, CHF) rows generated by `scripts/generate_synthetic_chf_gp.py`, reproducible from `generation_log.json` (seed 42).

**Method:** fit a Gaussian Process (Matern-5/2, ARD length scales — same kernel family as the project's existing GPR baseline) on 2,000 real training points, then sample the *posterior* (not the mean — sampling is what makes this generation rather than smoothing) at 8,000 query points drawn uniformly at random **off the discrete 24×21×23 grid**, restricted to P ≤ 16,000 kPa so no synthetic point ever enters the Split C extrapolation region. Each candidate is checked against the deterministic grid-interpolation baseline and rejected if it disagrees by more than a log-scale tolerance (a physical-plausibility filter, in the same spirit as the consistency checks reported in arXiv:2511.16207's diffusion-model paper). 88.9% of candidates passed.

**Why a GP and not the deep generative models in the recent literature:** two 2025 papers do this with a CVAE (arXiv:2409.05790, on this exact Groeneveld LUT) and a conditional diffusion model (arXiv:2511.16207). Both are stronger generators in principle. A GP was used here instead because (a) it needed no new heavy dependency — this environment doesn't actually have PyTorch installed despite `requirements.txt` listing it, so a CVAE wasn't a "quickly" option — and (b) the closest comparator group (Furlong, Zhao, Salko & Wu — see `docs/references/`) themselves use a deep Gaussian process as one of their three interchangeable generative/UQ techniques, so this isn't an ad hoc substitute, it's a technique straight from the adjacent literature.

**What this is for:** densifying the interior of the training domain to fight the exact failure mode documented in `docs/SENIOR_REVIEW.md` — tree models memorizing discrete grid nodes rather than learning a continuous surface. Use it as *training-set augmentation only*.

**Re-audited 2026-09-01, because "trust but verify" — here's what I checked and what it means:**

- ✅ **The off-grid claim is real.** Synthetic points sit a real distance from the nearest actual grid node (mean normalized distance 0.0245, i.e. genuinely interior, not just jittered copies of existing rows) — confirmed by nearest-neighbor search, not just asserted.
- ✅ **The posterior-sampling claim is real.** Values were drawn from the GP's predictive distribution, not its mean; posterior std (log scale) is well-behaved (median ≈ 0.17, i.e. ≈19% relative uncertainty per point) — this is genuine sampling, not disguised smoothing.
- ⚠️ **The 88.9% acceptance rate is not evidence the filter is too loose — but for a more specific reason than "the tolerance was generous."** Checking the actual accepted points: median deviation from the GridInterp reference is only ~10.7%, mean ~13%. The filter accepts almost everything because a GP trained on real LUT data naturally tracks grid interpolation closely in the interior — expected, and reassuring on its own.
- 🚩 **But that closeness is exactly what makes this data non-independent of GridInterp, and I should have said this more plainly the first time.** Every accepted synthetic CHF value was, by construction, filtered to agree with GridInterp to within a log-scale tolerance. **A model trained with this augmentation is being partially pulled toward GridInterp's own behavior.** That's fine for the stated purpose (densifying the interior so tree models stop memorizing discrete grid cells) — but it means: **this data must never be used, directly or indirectly, to support a claim that an augmented model "beats" or "outperforms" GridInterp.** Any such comparison would be partly circular. If you report results from a model trained with this augmentation, always also report the real-data-only version side by side, so a reader can see how much of the improvement (if any) is coming from real data vs. from data manufactured to resemble a baseline you're also comparing against.
- Also unaddressed: unlike the project's own PINN (`chf_physics.py`, monotonicity/Zuber/positivity penalties), this generator's only physical check is agreement with GridInterp — it does **not** independently verify monotonicity in X or the Zuber pressure trend. A point could pass the filter while locally violating one of those if GridInterp itself is locally noisy there (rare, but not impossible near grid edges).

**What this is not for:**
- **Never mix into Split C or any held-out test set.** These points were generated from a GP fit to real data and checked against a real physical baseline — using them as "ground truth" to evaluate a model would be evaluating a model against its own prior, not against reality.
- **Not a replacement for the real ~24,579-point NRC/OECD-NEA CHF database.** That database is confidential and distributed only on request from OECD/NEA or to registered AI/ML-benchmark participants (see `data/raw/external/README.md`); this file is a same-domain densification of the smaller Groeneveld LUT already in this repo, not new physical evidence.
- **Not yet upgraded to a CVAE/diffusion model.** If PyTorch becomes available in the working environment, re-implement using the CVAE architecture from arXiv:2409.05790 for a stronger, literature-matched result — this GP version is the fast first pass, not the final word.

## If you re-run the generator

```bash
python scripts/generate_synthetic_chf_gp.py
```

Regenerates both files deterministically from the seed in the script. Change `N_QUERY_POINTS`, `CONSISTENCY_TOL_LOG`, or `GP_FIT_SUBSAMPLE` at the top of the script to tune density vs. strictness; the acceptance rate and kernel hyperparameters are always logged to `generation_log.json` so a change is traceable.
